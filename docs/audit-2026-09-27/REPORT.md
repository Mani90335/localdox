**Localdox — product quality, performance, and persistence audit**  
27 September 2026 · Current working tree based on `83262d429a37c84555b4d334a782895dc5ac16c6`

**Decision: do not approve this version against the exceptional-quality bar requested.**

The reading surface has restraint, useful typography, and considerable engineering behind it. Several optimizations are already working. However, the product currently fails more fundamental promises: concurrent tabs can overwrite documents, backup restoration loses user state, search can retain obsolete filenames, and a moderately large stepped diagram can become a 52,311-pixel-tall page. Those failures outweigh visual polish.

This is an independent assessment using the quality expectations in your brief. It is not an assessment on behalf of Apple, Airbnb, Obsidian, Linear, or Arc, and no defensible numerical percentile can be assigned without a comparison dataset.

The recommended work is sequenced in [PLAN.md](PLAN.md). Priorities below mean **P0: release blocker involving data/trust; P1: major usability or performance defect; P2: important hardening or polish; P3: maintenance**. Evidence is labeled **reproduced**, **measured**, **source-confirmed**, or **design judgment** so hypotheses do not masquerade as measurements.

**Scope and method**

Inventoried the 311 source files and inspected the critical dependency, rendering, persistence, workspace, search, import/export, PDF, diagram, math, office, board, interactive-content, AI, and navigation paths. Built the current working tree, inspected emitted assets, ran unit tests and the existing browser suite, and exercised synthetic workloads in isolated browser contexts. Existing application edits were preserved; this audit adds reports and reproducible harnesses only.

DevTools MCP was not exposed in this session. Profiling used Playwright with Chrome DevTools Protocol: Performance metrics, precise JavaScript coverage, CPU/network throttling, and a loadable DevTools timeline trace. Browser: Chromium 153.0.8010.12 on the local macOS host. Production preview: `127.0.0.1:4176`. Cold runs used fresh browser contexts, 4× CPU slowdown, 150 ms network latency, 1.6 Mbps download, and 750 Kbps upload. Other measurements were unthrottled unless stated. Desktop viewport was 1440×1000; mobile checks used 390×844, including a separate touch-enabled context.

These are local laboratory results, not field INP, production CDN measurements, or physical-device frame-rate measurements. The cold profile used precise coverage, which can add overhead. Interaction durations are Event Timing entries, not a reported site-wide INP percentile. Heap snapshots below are samples without forced GC and exclude GPU/native allocations. Stress cases are single runs; the three cold loads are the only repeated page-load sample. The storage workload contains repetitive synthetic strings and is unsuitable for extrapolating real disk throughput. Remote sharing and paid AI requests were not executed. Safari, Firefox, actual low-memory phones, assistive-technology sessions, and a complete security penetration test remain outside this audit.

**What should be retained**

The v2 database separates file records from workspace metadata, uses a summary store, commits writes on transaction completion, migrates atomically, and avoids re-putting unchanged files. Scroll position no longer rewrites document payloads. Markdown structure parsing is deferred. Mermaid is viewport-gated, ordinary renders share in-flight results, large supported graphs have a worker/WASM/WebGL path, and the GPU renderer has cleanup. PDF rendering is limited to one or two pages with cancellable render tasks. Spreadsheet viewing virtualizes rows and its editor virtualizes wide columns. Conversion runs in a terminable worker. Math engines, syntax highlighting, office parsers, AI panels, and boards have lazy boundaries. CSS Highlight ranges preserve the document DOM. These are material strengths, not cosmetic optimizations.

**UI/UX assessment**

The strongest surface is ordinary reading: the palette is restrained, headings have a clear hierarchy, line lengths are comfortable, code and tables are distinguishable, and the sidebar is visually quiet. The weak point is the overall interaction contract. A reader should always know where they are, which file is active, whether an action changed a local copy, whether that change is durable, and whether content is leaving the device. Those answers are currently distributed across hidden menus, ephemeral toasts, and implementation assumptions.

**Engineering assurance**

The production build completed after allowing its local prerender server to bind a port. **198 unit tests passed, type checking passed, and all 19 existing end-to-end tests passed against the production preview.** This is useful coverage for conversion, editing, media, and highlighting, but the reproduced corruption/round-trip/search failures are outside that coverage.

The focused lint command over `src tests build vite.config.ts` reports **76 errors and 30 warnings across 37 files**: 46 explicit-`any` errors, 30 formatting errors, 15 hook-dependency warnings, and 15 refresh-export warnings. An earlier whole-repository lint reported additional formatting errors outside that focused scope. Do not treat formatting debt as equally severe as data loss. Establish a clean baseline and then prevent new regressions.

`DocsApp` is approximately 3,300 lines, MarkdownViewer approximately 1,780, and Sidebar approximately 1,110. Line count is not a performance diagnosis, but these components combine persistence, navigation, import, pane state, errors, and UI. A state/service split should make transaction ownership and lifecycle behavior explicit. No checked-in `.github` CI workflow was found; external CI may exist. There is no demonstrated enforcement of bundle, long-task, memory, durability, or accessibility budgets. Two package lockfiles are present; designate and enforce one installation path for reproducibility.

**Reference standards and product gates**

Use field p75 LCP ≤2.5 s, INP ≤200 ms, and CLS ≤0.1 as baseline web-health gates, not as proof of exceptional product quality. [Google's Core Web Vitals guidance](https://developers.google.com/search/docs/appearance/core-web-vitals) and [threshold methodology](https://web.dev/articles/defining-core-web-vitals-thresholds) support those baselines. For this app, also enforce operation-specific latency, memory, recovery, and focus gates in the plan.

Support text enlargement and usable zoom according to [W3C Resize Text guidance](https://www.w3.org/WAI/WCAG21/Understanding/resize-text); target sizing and other requirements come from [WCAG 2.2](https://www.w3.org/TR/wcag/). Persistent browser storage is requested through [StorageManager](https://developer.mozilla.org/en-US/docs/Web/API/StorageManager), with the result surfaced honestly. The Gemini recommendation follows [Google's current retirement schedule](https://ai.google.dev/gemini-api/docs/deprecations).
